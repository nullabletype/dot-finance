## .NET coding standards

The root `.editorconfig` uses the defaults generated by the .NET 10 SDK's `dotnet new editorconfig` template, with trailing whitespace removed. `Directory.Build.props` enables nullable reference types, implicit usings, built-in .NET 10 default analysers, and build-time code-style analysis for projects underneath the repository root. `global.json` selects SDK 10.0.401 with stable patch updates in the same feature band.

Once a project or solution exists, restore it, build it, and run the following check with its actual path:

```sh
dotnet format <project-or-solution> --verify-no-changes --no-restore --severity info
```

The explicit severity includes suggestion-level style rules. No StyleCop or third-party formatting convention is added. Prototype CI must run this gate alongside the build and LikeC4 checks.

With the .NET 10 SDK selected by `global.json` and a Node release accepted by `package.json` installed:

```sh
npm ci
npm run build
npm run smoke
npm run persistence:smoke
npm start
```

The full build validates and generates LikeC4 documentation, restores locked .NET dependencies, builds, tests, checks formatting, and publishes both the framework-dependent desktop prototype and the self-contained production shell. Smoke mode needs a graphical desktop; on Linux use `xvfb-run -a npm run smoke` in CI. The persistence smoke is non-graphical. All development uses synthetic financial data; the shipped application must remain offline.

## Production foundation

[ADR-0003](docs/adr/0003-production-boundaries.md) defines the production boundaries in `DotFinance.slnx`. The minimal Avalonia host is under `src/DotFinance.Desktop`; the pure reconciliation domain, encrypted vault, and strict Emma XLSX import adapter are implemented behind separate boundaries. The production desktop workflow does not expose them yet.

```sh
npm run production:build
npm run production:smoke
npm run production:start
```

`production:build` checks evaluated project/package/source boundaries, runs their negative checks, verifies formatting and publishes a self-contained trimmed executable for the current target. Native graphics libraries are bundled and privately extracted by .NET at runtime, as approved by the owner. No separate .NET installation is required. Build outputs stay under `artifacts/production/<rid>/`; they are validation output, not release packages.

`production:smoke` copies only that executable to an isolated directory, renders a native window, and verifies cold launch, cache reuse, missing-library recovery, replacement with a distinct test bundle, and rollback using the same cache. The update variant changes assembly version metadata only; it is not a release. A graphical desktop is required (`xvfb-run -a npm run production:smoke` on Linux). Receipts identify the source commit, binary hashes, target and whether the source was dirty. Screenshots and receipts remain local or in the job workspace, never Actions artifacts.

The full `npm run build` includes production checks alongside the retained prototype regression suite and LikeC4. Native CI covers macOS arm64, Windows x64 and Linux x64; macOS x64 is a publish target but native verification remains pending. Signing, installation, private real-data trials, and release packaging remain later gates. The app does not implement an updater.

See [single-file feasibility and the extraction decision](docs/development/single-executable-feasibility.md) and [dependency support review](docs/development/production-foundation-support.md).

The production reconciliation domain and its test evidence are described in [the domain implementation record](docs/development/reconciliation-domain.md). Run `npm run domain:mutations` for the six isolated mutation checks; the full build includes them. The current desktop window does not yet expose these domain operations.

## Private import-format inspection

The local [private XLSX export inspector](tools/DotFinance.ImportInspector/README.md) converts an owner-held workbook into a reviewable JSON structure report and a fixed representative synthetic XLSX workbook without writing the input path, worksheet names, arbitrary headers, original cell values, workbook metadata, or exact financial aggregates. Its approved findings underpin the versioned [Emma XLSX import contract](docs/development/emma-xlsx-contract-v1.md). The inspector remains development evidence tooling and is not part of the production application.

The production adapter and its pinned runtime dependencies are covered by the [import dependency support review](docs/development/import-dependencies.md).
